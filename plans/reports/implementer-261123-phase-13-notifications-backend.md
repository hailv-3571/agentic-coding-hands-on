## Decisions

- **Type names:** the DB enum uses the contract names (`kudo_received`, `secret_box_granted`, `kudo_hidden_spam`, `icon_set_completed`, …), not the plan's older names. The migration test checks that the DB enum equals the contract list.
- **Event Zod:** I reused the shared strict contract `domainEventSchema` (C-03) rather than duplicating per-type schemas in `features/notifications/schemas`. There is one source of truth, and drift between producer and consumer is impossible.
- **Consumption (single consumer of `consumed_at`):** grep confirms that nothing else reads or writes the column.
  - A drain reads the 50 oldest pending ids without a lock.
  - Each event then gets its own transaction: `SELECT … WHERE pending FOR UPDATE SKIP LOCKED`, then map, then write the notifications and `consumed_at` together.
  - UNIQUE(event_id, recipient_id, type) is the final guard.
  - Each event is tried at most once per run, so retries are spread across runs.
  - On error the event is rolled back and gets `attempts+1` and `last_error`. When attempts reach 5, `failed_at` is set and a `console.error` is logged.
  - A malformed payload or unknown type is consumed, gets `last_error` = "malformed …" (paths only, no values) and a `console.warn`.
  - A recipient whose profile was deleted is skipped (`INSERT … SELECT FROM profiles`), so it never causes a retry loop.
  - Rows carry the **event's** `occurred_at`, not the drain time.
- **Hearts:** an upsert on the partial unread index does `count+1` and sets `occurred_at = greatest(old, event)`. Once the row is read, the next heart opens a new row. Hearts have no actor, so the giver is never stored.
- **Tier-up "before" rule:**
  - after = `tierFromCount(HeroTierQuery.getDistinctSenderCounts([recipient], tx))`, read inside the event's transaction.
  - before = the highest tier this recipient has already been notified of (the `hero_tier_up` dedupe keys).
  - A notification is owed only when after ranks above before. The partial UNIQUE index is the guard against concurrent drainers.
  - Why: there is no second counting query (C-04), and the result stays correct when events are drained late, in bursts or out of order. A positional count would need a new phase 09 export. This rule reports the tier reached once.
  - A jump over several tiers reports only the top one, and a drop caused by spam never re-arms a tier.
  - As in spec ALG-002, a recipient's first public kudo also gives "New" (`tierFromCount(0)` is null).
- **Privacy:**
  - `actor_id` is null for an anonymous kudo.
  - The list query decides anonymity from the kudo's **current** state, because anonymity is editable. It selects the actor's name only for a kudo that is not anonymous now, and the nickname only for one that is.
  - National kudos use `items[].senderId` only to pick the recipient. Params are `{items:[{kudoId,rank}]}` and the view exposes `rank` plus the link to the best-ranked kudo.
  - The realtime payload is `{notificationId,type,occurredAt}` (+ `id` from `realtime.send`).
- **Destinations (Figma doc):**

  | Type | href |
  |---|---|
  | kudo types (received, heart, hidden) | `/kudos/{id}` (the owner can see their own hidden kudo) |
  | Secret Box | `/kudos?secretBox=open` |
  | tier-up and icon set | `/profile` |
  | national kudos | `/kudos/{topKudoId}` |

  The inline "Tiêu chuẩn cộng đồng" link is UI copy that points to `APP_ROUTES.communityStandards`.
- **Realtime:** topic `notifications:{userId}`, event `notification`. The policy requires the join topic **and** the row's own topic to equal `'notifications:' || auth.uid()`, broadcast only (phase 11 lesson). There is no INSERT policy. The phase 11 spotlight policy test is still green.
- **Cron:** follows phase 10. pg_cron runs '5 seconds' (pg_cron 1.6.4 locally). The Vault secrets are `saa_notifications_drain_url` and `saa_outbox_drain_secret`, sent in the `x-drain-secret` header. Where pg_cron, pg_net or Vault is missing, the migration only raises a NOTICE. The drain route answers 503 while unset, 401 for a wrong secret (constant-time compare), 200 `{processed, malformed, retrying, failed}`, and 500 `unexpected`.
- **Routes:**
  - Both read routes return 401 `unauthorized` before any read, and use `private, no-store`.
  - The list route returns 400 `invalid_request` for a bad limit or cursor, clamps `limit` to 50 (default 20), and returns `nextCursor` (phase 05 µs cursor codec).
  - The actions use `requireSunner()`, so a guest is redirected to /login. A foreign, unknown or malformed id gets the same `{ok:false,code:"not_found"}`. On success they return `{ok:true, unread}` or `{ok:true, updated, unread}`.

## Concerns
1. **Local e2e drain.** No Vault secrets are set locally, so the cron sends nothing and the bell only updates when something drains. For e2e: set `OUTBOX_DRAIN_SECRET` (at least 32 characters) for the dev server and have the e2e POST `/api/internal/notifications/drain` with `x-drain-secret`. Do not set the local Vault secrets during integration runs: the cron would drain concurrently and race the failure, malformed and spy assertions.
2. The tier-up rule deviates from spec ALG-002 (positional count), for the reasons above. The plan's "add a positional export to phase 09" is not needed.
3. `cron.job_run_details` grows by about 17k rows a day at 5 s; it needs the usual pg_cron housekeeping in production.
4. Unknown event types are consumed, as the spec says. A future producer must ship its consumer first.
5. `last_error` may contain driver text, including SQL parameters (ids). It is server-only: RLS with no grant.
6. `actor_id` is ON DELETE SET NULL. If an actor's profile were deleted, a non-anonymous kudo would lose its name, and the UI would show the nameless copy. Only test cleanup deletes profiles.
