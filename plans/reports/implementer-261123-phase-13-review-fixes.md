## M1: retry backoff

**Root cause.** `pendingEventIds` and the locked re-read only checked `consumed_at`/`failed_at`. A failing event was retried on every drain tick (every 5 s) and parked after 5 attempts, about 25 s after the first failure.

**Fix** (`features/notifications/server/notification-event-processor.ts`):
- New nullable column `domain_event_outbox.next_attempt_at` (null means retry now). The outbox had no last-attempt timestamp, so this is the smallest schema change that works.
- One shared predicate, `PENDING_AND_DUE`: `consumed_at is null and failed_at is null and (next_attempt_at is null or next_attempt_at <= now())`. Three places use it:
  1. the candidate scan;
  2. the per-event `FOR UPDATE SKIP LOCKED` re-read;
  3. the `recordFailure` UPDATE.
- On failure: `next_attempt_at = now() + make_interval(secs => 60 * 2^attempts_before)`. The waits are 1, 2, 4 and 8 min, so the 5 attempts span about 15 min. The base delay is the constant `OUTBOX_RETRY_BASE_DELAY_SECONDS = 60` in `features/notifications/notification-config.ts`. `OUTBOX_MAX_ATTEMPTS = 5` is unchanged.
- Locking still holds:
  - The per-event lock, SKIP LOCKED, and writing `consumed_at` in the same transaction are unchanged.
  - The guard in `recordFailure` means two overlapping drains that both fail the same event count only one attempt: the second UPDATE sees the event is not due yet and does nothing.
  - An extra try by a concurrent drainer stays harmless because of the UNIQUE guard and the `consumed_at` check.
- Malformed or unknown events are still consumed and logged (that test is unchanged and green).

**Manual reset for replay** (also in the processor docblock and the 0021 header):

```sql
-- replay every parked event once the cause is fixed; the next drain picks them up
update public.domain_event_outbox
set failed_at = null, attempts = 0, next_attempt_at = null
where consumed_at is null and failed_at is not null;
-- a single event: add  and id = '<event uuid>'
```

The replay is safe: the locked re-read, `consumed_at` in the same transaction, and UNIQUE(event_id, recipient_id, type) all still apply.

## M2: `event_id` FK

**Does de-duplication depend on a non-null `event_id`?** No, so SET NULL is safe:
- UNIQUE(event_id, recipient_id, type) only has to stop the *same event* being processed twice.
- The processor always inserts a non-null `event_id` (`e.id` from the joined outbox row).
- SET NULL fires only when the outbox row is deleted, and a deleted event can never be drained again. A NULL `event_id` therefore never needs to collide with a new insert. Postgres treats NULLs as distinct, but that only affects these historical rows.
- The heart and tier de-duplication keys (`recipient_id, dedupe_key`) do not use `event_id`.

RESTRICT was rejected: it would block outbox pruning unless notification history were deleted first.

**Fix:**
- `shared/db/schema/notifications.ts`: `eventId` is nullable with `onDelete: "set null"`, and the comments are updated.
- `db/migrations/0021_notifications_retry_backoff_and_event_fk.sql`: generated by drizzle-kit with a header comment added. It drops and re-adds the FK, drops NOT NULL, and adds `next_attempt_at`.
- `db/migrations/0021_notifications_retry_backoff_and_event_fk.down.sql`: deletes rows whose `event_id` is null (what the old cascade would have done), restores NOT NULL and the CASCADE FK, and drops the column.
- `db/migrations/meta/0021_snapshot.json` and the journal entry (idx 21). A semantic diff against 0020 shows only three changes: `next_attempt_at` added, `event_id.notNull` true → false, FK `onDelete` cascade → set null. Everything else is key-order noise from drizzle-kit.
- Migrations 0018–0020 were not edited.
